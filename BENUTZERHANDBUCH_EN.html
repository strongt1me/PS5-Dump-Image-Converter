1 Welcome

This manual is intended for everyone who is using the PS5 Dump & Image Converter for the first time. It explains the visible buttons, the safe standard workflow, all eight tasks, and the additional tools in the top bar – in plain language. You do not need to know any technical details about file systems or container structure.

The most important point in one sentence

Choose the matching task on the left, specify the source, target format, target folder, and temp folder – and only then start processing.

1.1 What you need before you start

Safety rule for the beginning

Delete or overwrite the original files only after the result has been created successfully and, if needed, checked with Task 8 – Validator.

2 The interface in 60 seconds

On the left you choose one of the eight tasks. On the right, only the fields needed for that task appear. The large area below START shows messages and results while the work is running. Below the tasks, the sidebar shows the cover image of the selected game with its name underneath. Above the cover, the sidebar shows the firmware the game needs and – if a backport is built in – its firmware. Game Info and the resources window have no system frame: you can drag their sides and lower corners to make them larger, and under Windows 11 their corners are rounded.

AreaMeaning
SOURCEThe file or folder to be processed. You can also drag it from File Explorer into the field (drag & drop) – this works just as well for TARGET FOLDER and TEMP FOLDER, even when the program is running as administrator. As long as a field is empty, a gray hint shows what belongs in it (depending on the task, a dump folder or a specific file).
TARGET FORMATDetermines whether a dump folder, .ffpfsc, .ffpfs, .exFAT, or .ffpkg is to be created. Appears only when it is needed.
COMPRESSION (PFS)How strongly the data is packed – 1 is fastest, 9 is smallest. To get started, “6 – Balanced” is enough.
WORKERSHow many work processes run at the same time. One core always stays free; very large images are additionally throttled. Since v1.8.92 the value is set with a rotary knob: turn it while holding the mouse button, change it by one with the mouse wheel or the arrow keys, and reset it to the default with a double-click. The current number is shown in the center of the knob. Move the mouse over it and the hint shows what your setting actually does.
PRESETFour buttons to the right of the checkboxes at the bottom of the path card set the compression level and the core count with one click: Fast (level 3, all cores), Balanced (level 6, half the cores), Maximum (level 9, half the cores), and Low RAM (level 3, one core – only one worker uses memory, but it takes longer). The button whose values are currently set is highlighted; if you change the level or workers by hand, the highlight goes out. The block size stays at 65536: smaller blocks gained 0.1% in measurement, and 64 KB is the unit with which ShadowMount+ mounts the image. In a very narrow window the buttons are dropped instead of overlapping a checkbox. The idea comes from PS5-FFPFSC-PRO 1.3.0.
VERIFYWhether the finished image is checked after packing. “Quick” checks the structure and a sample of the blocks (about 1 %, at most 1 GiB), “Full” additionally reads everything back and takes considerably longer, “Off” checks only the structure. Task 8 can also check at any time afterward.
TARGET FOLDERThe program writes the finished result here. It is best to use a different folder than the source. The field starts empty; the selection dialog opens in the most recently used target folder.
TEMP FOLDERSince v1.9.98 the field appears only where an intermediate folder is still created (when the conversion without an intermediate folder is switched off, or with AMPR EMU and an LZ4 asset pack, where a run may exceptionally still need an intermediate folder, Section 3.3); otherwise it stays hidden, and a folder chosen earlier remains in effect. The field starts empty; empty means: the Windows temp folder, without it appearing in the field. Storage for temporary working files. Best is a dedicated folder on a large drive (e.g. D:\PS5-Temp): in the Windows temp folder, Windows storage optimization may delete files when space is low – even a working copy in the middle of a run. If the temp folder is located there and deletion is enabled, the log warns you when a run starts.
Dump folder in the work folderCheckbox in the path card. When repacking (for example .ffpfsc → .ffpkg), the program first unpacks the source into a temporary dump folder. By default this is placed at the target; if the box is checked, it moves to the work folder – then only the finished result is created on the target drive. The work folder must be able to hold the complete dump for this. Pure unpack tasks are not affected: there the dump folder is the result.
Dump folder: create a working copy firstCheckbox below it. If something has to be integrated into an existing dump folder (BACKPORT, AMPR EMU, asset pack, PlayGo), the program creates a working copy without asking (for Task 1, a backup in the target folder) and works in it – the original stays unchanged, and a run does not have to wait for your “Yes”. Without the check mark, you are asked as before.
Shut down computerCheckbox in the path card. If it is checked, the computer shuts down by itself after a successful run – see Section 3.2.
STARTBegins the selected task as soon as all required information is present.
CANCELRequests a controlled cancellation. Afterward, wait until the program confirms the cancellation.
Live displayAt the right below the log, the load is shown once per second during a run: “CPU: 42% | RAM: 9.00 GB free (15.00 GB / 24.00 GB) | Temp: …”. The free memory comes first, followed by used and total. If it drops below 1 GB, it reads “RAM: only … free” – at 0.8 GB, a build aborted with MemoryError on September 20, 2026. In that case the Low RAM preset or closing other programs helps.
Log areaShows understandable status messages, warnings, and the completion of the task. Every work step appears there with “[…]”; long steps (checking, checksums, transferring, working copy) report their progress every 10 % with the remaining time and, at the end, their duration. The status line below shows the same continuously (“… – 42 % · about 3:10 left” or “… – running for 1:23” when no percentage can be measured). When you choose a source, this area also shows what is already integrated in the game (BACKPORT, AMPR EMU, asset pack, PlayGo) and whether PlayGo would be needed – nothing is switched on in the process.

Nothing is preset on opening: AMPR EMU, PlayGo, and BACKPORT are off, AMPR EMU is set to Normal (without pack) with the newest version without a pack, and SOURCE, TARGET FOLDER, and TEMP FOLDER are empty. If TEMP FOLDER stays empty, the first task on Windows works in the folder Temp - Dump-Image Converter in the root directory of the system drive (usually C:\); the program then creates it and enters it in the field. On Linux and macOS, the system's temp folder applies. Whatever you check or choose during a session stays in place until you quit; the next time you start, everything begins empty again. The command line (--cli), by contrast, continues to read the most recently saved settings.

At the top right is the toolbar with additional functions (FILEZILLA, JS LOADER, CREDITS, THEME, and more). For a normal conversion you do not need these buttons – they are explained in Chapter 14.

2.1 The second view: CONSOLE

Below the logo in the sidebar, CONSOLE › switches to a second view. On the left it lists ten tools for working with the console: 1. Console & payloads, 2. WebKit Autoloader, 3. Library, 4. Prospero Manager, 5. CoolSysCent-Pro, 6. ShadowMount+, 7. SMPlusGui, 8. BFpilot, 9. AMPR EMU Manager and 10. AMPR trace. The cover image, “Game info” and “What else you might need” are not there. On the right is the page Console & payloads (see below); 2. WebKit Autoloader and 3. Library show their own page at this spot – none of the first three tools opens a window of its own. A second press on the same button changes nothing; 1. Console & payloads leads back. The kernel log is available as KLOG at the top of the title bar. ‹ CONVERT leads back – the selected source, the settings and a running job are kept. The program always starts in the CONVERT view – even if CONSOLE was open when it was last closed.

QR code. Below the table of 1. Console & payloads, the QR code button shows, for the selected service with a web interface, a QR code for your phone containing its address (http://<PS5-Adresse>:<Port>/); the phone's camera app opens the page. The same button is in the header of the pages with their own web interface. Phone and console must be on the same network; the code contains only the address, no access codes. It is generated in the program; nothing goes onto the network.

4. Prospero Manager, 5. CoolSysCent-Pro, 6. ShadowMount+ and 7. SMPlusGui, by contrast, do not show a page of their own: One press checks whether the payload is already running on the console, sends it itself if needed – together with the ELF loader if port 9021 is still closed – and then opens its web interface directly (Prospero Manager: port 7070, CoolSysCent-Pro: port 8086, ShadowMount+: port 10101, SMPlusGui: port 7777), exactly like Open web interface on “Console & payloads” (see below). Every step appears in the main log. If the payload first has to be sent, a small notice window shows what is happening – without a button, you do not have to confirm anything; it closes by itself as soon as everything is loaded. If the payload is already running, it does not appear. While one of these actions is running, the five buttons are locked: They share the ELF loader.

ShadowMount+ is a special case. Out of the box, its web interface listened only on the PS5 itself up to 1.7beta7 (api_bind_address=127.0.0.1); since 1.7beta8 it is 0.0.0.0. If it listens only on the PS5, port 10101 is closed from this PC even though ShadowMount+ is running – and the button sends the payload once more anyway. If the port does not answer afterwards, the log says so and gives the reason. So first set the key api_bind_address in the ShadowMount+ editor (MORE TOOLS) to the PS5 address or 0.0.0.0 – there is no login, so not on a network you do not control.

5. CoolSysCent-Pro is the PS5 Cooling & System Center (fan and temperatures, system info, game library, installing packages – all in the browser). Its web interface is on port 8086 out of the box and listens on all addresses (bind_address 0.0.0.0); the app sets both itself (http_port). If one of the two values was changed and the port stays closed as a result, the log says so and names the keys – then open the page by hand in the browser. The web interface accepts only requests that come via the IP address of the console. In the table of “Console & payloads” the app is listed like the other payloads, with its running version (the app reports it itself) and the Open web interface button.

8. BFpilot is a second file manager for the PS5 with a web interface on port 5905. It works like Prospero Manager: One press checks whether the payload (bfpilot_v0.4.4-multilang.elf from the folder helloworld) is already running on the console, sends it itself if needed – together with the ELF loader if port 9021 is still closed – and then opens its page on the right in the program (on Windows) or in the browser. According to the texts in the interface itself, it can browse files and folders, upload and download, rename, copy and delete, extract archives (rar, 7z, zip), edit text files, install packages, search via an SSD index and load payloads through the ELF loader; its log is at /data/BFpilot/log.txt. The page is multilingual (German, English, Spanish, French, Italian) and follows the system language of the console. Who wrote BFpilot and under which license it is released is not stated in the file. This path is untested on the console: The procedure (send payload, open page) matches that of the other buttons and has only been tested against simulations. Note from the page itself: Anyone who writes directly into a folder scanned by ShadowMount+ while ShadowMount+ is running can trigger a kernel panic.

Try the transfer with a small file first: How the console's FTP server behaves with resuming, renaming and free space has not been verified in general.

Console & payloads (right-hand side)

At program start, the program looks for the PS5 itself and connects: It finds its address and saves it, queries the services, loads the ELF loader if it is missing (see below), and afterwards sends your favorites (see below; FTP server and kernel log out of the box), as far as they are not running. You do not have to enter a PS5 address for this. The start and the result appear in the log of the main window; if no PS5 is found, the program carries on without a console.

The first button shows the same page on the right in the view – no window of its own – and searches again with every press: first at the saved address and the FTP profiles, then with the console search (broadcast, UDP 9302, the discovery protocol of Remote Play – the console answers even without any payload and in rest mode) and, if your router lets no broadcast through, address by address in your own network. No FTP service has to be running for this. The address found then appears in the field and is saved; only if no PS5 answers, enter it yourself and press Check console.

At the top, the page shows the name, state and firmware of the console – the firmware as the console itself writes it (12.00, 12.02, 12.70 …). Below that, it queries all twenty-nine known ports at the same time – ELF loader (9021 and 9020), Payload manager, FTP server, Kernel log, PKG manager, Web file manager, Garlic save manager, BFpilot, Web server, ShadowMount+, Prospero Manager, ps5upload, CheatRunner, App dumper, Game compressor, SMPlusGui, aria2, zftpd, gdbsrv, ps5debug-NG, AnyPad PS5, DPI v2 and the PS5 Cooling & System Center (port 8086), PS4Mount (port 8770), NeoEnabler (port 8765), exFAT2AMPR (port 6972), PatchDL (port 12880) and Home Hider (port 8090) – and shows the port, version and purpose for each; for the FTP server, the greeting is read along so that a hung service does not pass as “running”. The version is that of the bundled file the program starts. FTP server, Payload manager, the Cooling & System Center, PS4Mount, NeoEnabler, exFAT2AMPR, PatchDL, Home Hider and ShadowMount+ report their running version themselves (ShadowMount+ only if its interface is reachable from this PC); if it differs, for example because an older payload was started from elsewhere, the bundled one is shown in parentheses after it. For ShadowMount+, the second ELF loader port (9020) and DPI v2, the version of the accompanying file is shown, even though the program does not start them there. All other services do not reveal their version. Ports and web interfaces of the eight services added on October 2, 2026 (CheatRunner through ps5debug-NG), of AnyPad PS5 and of DPI v2 come from their authors' descriptions and have not yet been measured on the console. AnyPad PS5 (bundled: 0.9.1-beta) makes Bluetooth controllers usable on the PS5; games see them as a DualSense. According to the author, confirmed on a real PS5 are DualShock 4 v2, 8BitDo SF30 Pro (Switch mode) and GameSir G7 SE; Xbox, Switch Pro and other controllers are supported but not yet confirmed. Pairing is done on its web interface, which is open to anyone on the same network without a PIN (on the console also in the Media row). If the console asks who is using the controller, choose, according to the author, Quick Play/Guest (a temporary user); a DualShock 4 has to be paired again after every power-on. Always quit AnyPad with the button on its web interface, also before you start it again. DPI v2 installs PKG files through its web interface (port 12800 according to the author, adjustable; no login, so not on a network you do not control). It is a plugin for OnionHEN, sits on the console in the folder /data/OnionHEN/plugins and is started by OnionHEN – Start selected therefore does not send it. PS4Mount (gasb07, bundled: 0.5.1) plays PS4 fake PKGs directly from a USB drive, without installing them on the console: The PKG files (game, update, add-ons) belong in the main folder of an exFAT drive; on the first run, PS4Mount places them per game under /ps4/CUSAxxxxx on the drive. After sending (to the ELF loader), the games appear on the home screen. Its web interface (port 8770, no login, so not on a network you do not control; on the console also in the Media row) shows them and removes them from the library without deleting the PKG. PS4Mount reads the kernel log: Either klogsrv (port 3232) is running, or no other payload reads /dev/klog – otherwise the games do not start. According to the author, it runs on any firmware with fake PKG support (tested on 13.20; below 6.00 it registers each game individually); several drives connected at the same time can slow down the console's interface. The port and web interface come from the author's description and have not yet been measured on the console. NeoEnabler (gasb07, bundled: 0.3.0) starts PS4 games on the PS5 in PS4 Pro mode, according to the author up to native 4K, but only for the games it brings patches for. It requires ps-patch-system: Load it first after every start of the console and then send NeoEnabler (to the ELF loader). At startup, NeoEnabler loads its game patches from the author's project on GitHub and enters them into the files of ps-patch-system; before that, it backs these up under /data/neo-enabler/xml-backup. On its web interface (port 8765, no login, so not on a network you do not control; on the console also in the Media row) you choose the patch per game. The 8 GiB of memory that some patches need only works, according to the author, on firmware 13.20 (13.60 is still untested) and with the hypervisor unlocked; the GPU clock tab only appears on firmware 13.20 and is off by default. The port and web interface come from the author's description and have not yet been measured on the console. According to the author, you update CheatRunner (port 9999) in this order, before you send the new version: First, on the console, delete everything in /data/cheatrunner except the folders cheats and patches (not only afterwards). Second, delete the old CheatRunner PKG (the tile on the home screen) from the PS5. Third, clear the browser cache (Settings → System → Browser → Clear cache). The program deletes nothing on the console itself. What is not running, you start with Start selected or Send favorites directly from the bundled folder helloworld; services with their own web interface are opened by Open web interface. Every step appears in the log below. For ShadowMount+, the page deliberately offers no Start selected – it usually runs permanently from the autoload, and its web interface listened only on the PS5 itself out of the box up to 1.7beta7: There, Open web interface opens it from this PC only once you set the key api_bind_address in the ShadowMount+ editor (MORE TOOLS) to the PS5 address or 0.0.0.0 (since 1.7beta8 this is the default) – without authentication, so not on a network you do not control. The 6. ShadowMount+ button of the view sends the payload itself, by contrast, if port 10101 is closed (see above). If the console search does not answer but services are running, the page says so explicitly: The console is then there, but your router does not let the broadcasts through. Switching the view alone sends nothing onto the network.

Web interfaces in the program. On Windows, the web interfaces of the console – Payload manager, PKG manager, Garlic, Web file manager and the others – open inside the program and fill the whole area below the top bar; the sidebar steps aside for as long as that lasts. The header shows the name, address and state, plus Reload, Open in browser and ‹ Back to the page you came from. If you leave the interface, it is closed. It is displayed with WebView2, the browser engine of Edge, which is part of Windows. If it is missing or the program runs on Linux or macOS, the interface opens in your browser as before; the log then names the reason.

If the ELF loader (port 9021) is closed, the page loads it by itself via the Payload manager after searching and after Check console: If the folder /data/pldmgr/payloads/elfldr is missing on the PS5, it is put there via FTP (elfldr-ps5_v0.27.elf together with the companion file .json, as the Payload manager creates it itself); if it is already there, nothing is uploaded, only loaded. If no FTP server is running, elfldr goes through the web interface of the Payload manager as before. A different file under the same name is left untouched – the log then says that elfldr was not loaded.

Favorites. The first column of the table carries a star. A click on ☆ (or the space bar on the selected row) makes the service a favorite, another click removes it again; the line above the table names who is currently a favorite. Favorites are the payloads that the program sends to the PS5 by itself – at program start and on Send favorites. Out of the box these are the FTP server and the kernel log; Default restores that. Only what is not running is sent, in the order of the table; a service that is stuck is not sent again (see the box below). Port 9021 is part of every send: If the ELF loader is closed, the program opens it first in the way described above; if that fails, the favorites stay unsent, and the log says so. That is why the ELF loader needs no star; ShadowMount+ and DPI v2, which the program does not start itself, carry none either. If you hover the mouse over the row, you see the short instructions. The checkbox Send automatically at program start (on out of the box) only switches off sending at start; Send favorites remains your button. The choice is saved.

After sending, the page reads the output of a service only briefly (3 seconds of silence) and then polls its port until it answers. A service runs permanently and keeps the connection to the ELF loader open; every start used to wait 30 seconds because of that.

“Stuck” is something other than “not running”

For the FTP server, it is checked not only whether the port accepts connections but also whether it responds. An aborted download can put ftpsrv into a state in which it keeps accepting connections and then stays silent; reloading the payload does not help then, only a restart of the console. In this case the status light shows stuck and writes a warning to the log – an ordinary port scan would wrongly report “running” here.

Updates. At the top right in the header of the page, next to Check console, is Updates – it concerns the tools of the program, not the PS5, and stays usable while a service is being sent. The press opens a window and immediately asks each bundled tool's author for the latest release – the payloads in the folder helloworld, the WebKit Autoloader, AMPR EMU and the engines (MkPFS, UFS2Tool, LibProsperoPkg, OrbisPkgTool, PS5-PKG-Tool, PS5 Wee Tools, 7-Zip). This is the only network access; without the button, the program asks nowhere. For each tool the list shows the bundled and the latest version and a verdict: New version (can be ticked), Up to date, Bundled is newer (for example a pre-release build that the author has not yet published as such), New – install by hand (engines with their own adaptations, archives and tools without a version in the file name: only the verdict is shown here, and Release page opens the author's page), Not comparable and Unreachable.

Ticking is done in the first column (click or space bar); Select new and Deselect affect all at once, Download fetches the selection. Each file is checked against the size and SHA-256 of the release before it is put in its place (on Codeberg against the neighboring .sha256 file); a tool made of several files (WebKit Autoloader: host as .exe and .py, installer as ELF) arrives completely or not at all. If the release has no checksum, the log says so, and only the size was checked. Files are fetched to Werkzeug-Updates in the program's settings folder (on Windows %APPDATA%\PS5ImageConverterPro), never into the bundled folders; nothing that is bundled is deleted or overwritten. For each pattern the program takes the highest version from both locations: The table of this page, the quick selection for ELF files and the WebKit Autoloader page show the new file immediately; Start selected and the favorites send it too. The exceptions are elfldr, ftpsrv and klogsrv: For these, the program stays with the verified bundled file in the table, when starting (including the favorites) and in its own procedures; the fetched one is available in the quick selection for sending. AMPR EMU goes, as with the existing AMPR EMU update, into the folder AMPR EMU updates next to the program. Open folder shows the storage folder; you may delete fetched files there at any time.

Without a login, GitHub allows 60 requests per hour, and a full check needs around fifty. The program remembers every response together with its ETag; a second check only asks whether anything has changed, and such requests do not count. When the limit is reached, the window names the time from which it works again and shows the last remembered state with its date for the remaining sources.

Library

The library shows your backups as tiles across the whole width or as a list. Each card carries the cover image with the platform (PS4 or PS5), the title, badges for format and integrations and four buttons; there is no column with details next to it. At the top in the header card you choose the source:

  • This PC searches the registered SCAN FOLDERS including subfolders for dump folders, container files (.ffpfsc, .ffpfs, .exfat, .ffpkg) and packages (.pkg, .fpkg) – Add folder…, Remove, Rescan. If a registered folder is itself a dump folder, it is the one hit; its contents are not searched. A new search ends one that is still running.
  • PS5 finds the console itself and shows what is on it: the backups in the usual storage locations – internal, on USB drives and on the M.2 expansion – and in addition the installed games, PS5 titles as well as PS4 titles installed via PKG. The type entry tells them apart (“PS5 · installed”, “PS4 · installed (PKG)”). System applications of the console do not appear, and a game that also exists as a backup is listed only once – as a backup. Packages (.pkg, .fpkg) are not listed by the console side.

Progress while searching. If a search takes longer than a moment – images on a cold hard disk, packages of a hundred gigabytes, the console on the network – a window with a bar and percentage opens. It names the current stage, the folder or title the program is currently reading, and – as soon as the number of finds is known – “done of total”. On the PC, the stages are Searching folders, Reading details, Loading cover images and Checking integrations; on the PS5, Looking for the PS5, Searching the PS5 storage locations, Matching title IDs and Reading installed titles come before them. The percentage is a rough guide, not a promise: How long a stage takes depends on the files. Cancel (or the ✕) ends the search; the list stays as it was, and the status line says that it was cancelled. On the PS5, the cancellation takes effect between two FTP commands, never in the middle of a transfer. If you switch the page or restart the search, the window closes by itself; a search that finishes in a moment does not show it at all.

So that a second search is fast, the program remembers what it has read about an image or package – by path, modification time and size of the file. If the file is replaced, it reads it again; dump folders it reads fresh every time because that is cheap. In an .exfat image (also in an .ffpfsc or .ffpfs) it looks only into the few folders it needs – root, sce_sys and fakelib –, not into every directory of the game.

Packages. A .pkg or .fpkg carries the badge PKG or FPKG on its card. The program reads title, ID, version, firmware and cover image from the header of the package – it never loads the file, not even at a hundred gigabytes. If an entry in the package is encrypted, the corresponding details are missing; the program then fills in ID and title from the content ID and the file name. Copy is locked for packages: A package is installed on the console, not mounted, and the storage locations that Copy sends to are for images and dump folders. Convert works only for a .pkg of a PS4 title: It opens the window PS4 PKG Dump & Image Converter with the file already entered. The program does not convert an .fpkg and a PS5 package. A package carries no integrations; its card therefore shows neither badges nor a line for them.

The header card summarizes what is currently shown. Source and view are chosen with the two switches at the top right (This PC | PS5 and Tiles | List); the one that currently applies is highlighted. Below it, the count line states how many games there are (“25 games · 10 PS5, 15 PS4 · 4 with BACKPORT, AMPR or PlayGo”; during a search “3 of 38 games”). 3 The safe standard workflow

Follow the same order for every conversion. This avoids the most common selection mistakes.

  1. Click the task you want on the left.
  2. Choose the source with the button to the right of the SOURCE field.
  3. If shown, choose the TARGET FORMAT and, if needed, the compression level and worker threads.
  4. Choose a separate TARGET FOLDER. Normally you no longer need to choose a TEMP FOLDER: the conversions work without an unpacked game, and the field appears only where an intermediate folder is created (Section 3.3).
  5. Check all paths once more and click START.
  6. Leave the program open until the log reports a successful completion.
Recommended first test

Start with a copy of a small set of test data. Check it first with Task 8. Then run a conversion and inspect the result before you use larger data.

3.1 Reading the progress correctly

While a task is running, the bar shows the overall progress, and the same value appears next to it as a percentage. For larger conversions, the status line adds phase information (such as “Phase 3/4 – …”) and, where available, a line with the current CPU, RAM and temp storage usage. These displays are updated together.

Below it, the stage line shows each section of the run with its state and duration, for example ✓ System files 0:03 · ▶ Integration 1:30 (Measure 1:10) · ○ Write · ○ Check · total 1:33. A check mark means done, a triangle is running right now, a circle is still waiting; after the run the line stays with the final times. The same times appear in the log as [ZEIT].

While processing

Do not force the program to close and do not disconnect the drive. If you use CANCEL, wait for the completion message. Do not keep using an incomplete result.

3.2 Shutting down the computer after the work is done

Large conversions take a long time. With the checkbox Shut down the computer after a successful run (in the path card) you can leave the computer alone while it works.

This is what happens when the task was successful:

  1. A window appears and counts down 60 seconds. During that time you can object with Cancel – keep the computer on or the ESC key.
  2. After that, the program detaches all mounted images, removes the temporary work files and writes the log to disk.
  3. Only then does Windows shut down – without any further prompts.
Nothing happens after an error

After an error or after CANCEL, the computer stays on so that you can read the message in the log at your leisure. That is exactly why the function is tied to the result of the task and not merely to its end.

  • The shutdown happens without prompts and also closes other programs. Unsaved work in other windows is lost – save it beforehand.
  • While the checkbox is checked, no success message that you would have to click away appears at the end; it would wait for a confirmation that nobody gives. The success is shown in the status line and in the log.
  • If the AMPR recording assistant (section 11.1) is running, the computer stays on – it still has to restore on the console what it changed. The log then says so.

The setting is saved and also applies at the next start. In command-line mode, the switch --shutdown-on-success takes care of this.

3.3 When there is not enough space

Before the start, the program calculates how much space the task needs – separately for the target folder and the work folder. If there is not enough, the task does not simply start. A window appears that states, for each folder, what is needed, what is free and what is missing.

Your choiceWhat happens then
Choose working folder…You pick a different work folder; the calculation is then repeated.
Choose target folder…The same for the target – the other folder can also be too tight.
Start anywayThe task starts at your own risk.

How much is needed depends on the target format: a .ffpfsc needs about 0.75 times the source size, .ffpfs and .exFAT 1.1 times, a .ffpkg 1.3 times. If the work folder and target folder are on the same drive, the sum is checked – viewed separately, each would look fine, and together there would still not be enough.

A game is converted without an intermediate folder: the program reads it directly from the source (.exFAT, .ffpfs, .ffpfsc, .ffpkg or dump folder) and writes the result in one pass. Even with AMPR EMU, BACKPORT, fake signature, DLC EMU and PlayGo, the work folder holds only the few files that the integration changes (about 5 % of the source, at least 2 GiB); the space is then needed mainly by the target. This applies equally to asset packs with zstd and with LZ4. A .ffpkg is created without UFS2Tool and without administrator rights.

Only where the stream does not work, a complete working copy is created in the work folder as before, and the space needed there is as large as the game itself: with a pack profile of your own <Ordnername>_ampr_pack.toml next to the dump folder, with a title profile with several groups (such as EA Sports UFC 6), if the source already carries a packed asset layer or contains symbolic links, and with a .ffpkg with names that the image cannot hold. The log states the reason ("… packing goes through an intermediate folder as before") and warns if the work folder is too small for it. The field TEMP FOLDER in the main view appears only where the conversion without an intermediate folder is switched off or AMPR EMU is built in with an LZ4 asset pack (there a run may exceptionally still need an intermediate folder); a folder once chosen there remains in effect, and through the “When there is not enough space” window another work folder can be chosen.

There is no window on the command line: There, the finding is reported, and --yes decides as it does for any other prompt.

3.4 Lots of data or texture streaming: stuttering possible

For games with a very large amount of data or texture streaming, stuttering is possible in a .ffpfsc or .ffpfs. Before either of them is created, the program therefore checks the source – regardless of its format – and asks if the game stands out:

  • Lots of data: from 50 GiB.
  • Texture streaming: files that typical streaming engines create (for example .ubulk, .ucas, .utoc, .streamdb, .resS, .cas), large files with “stream” or “texture” in the name, and folders such as StreamingAssets – these count from 20 GiB.

Folders and .exFAT images are scanned for this without unpacking anything. For .ffpfsc, .ffpfs, .ffpkg and packages, only the file size counts; for a compressed file, the real amount of data is higher, and the message then says “at least”.

3.5 Before the start, after an error and when naming

Pre-check. Before the start, the program goes through the game folder once and reports all findings at the same time; the affected paths are in the log. For an exFAT image, names outside ASCII, symbolic links, invalid characters and names that differ only in upper and lower case are errors – the writer would reject them only after copying. For .ffpkg, .ffpfs and .ffpfsc they are a warning; there it is not proven. There are also warnings for paths deeper than 32 folder levels and for an output name over 63 bytes (for .ffpfsc 58) that might no longer fit after the ShadowMount+ mount path; this has not been measured on the console. A FAT32 target is also an error if a file is over 4 GiB. Batch conversion checks only the output names; the name probe reads for 20 seconds at most. A probe that itself fails never prevents the start.

Output name by template. By default the result is named like the source. Under SETTINGS, section OUTPUT NAME, you build the name from the details of the game, for example {title} [{title_id}] v{version} (Astro Bot [PPSA01234] v1.0.0). The parts are {name} (name of the source), {title}, {title_id}, {version}, {region}, {fw} (minimum firmware) and {pack} (zstd or lz4, empty for a game without an asset pack); each at most once, and at least {name}, {title} or {title_id} must appear. The example list and the preview show the name of a sample game for each format, with the bytes against the length limit; Default resets to {name}. A usable template is saved immediately; for an unusable one the reason is shown and the last saved one stays in effect. A generated name is cut to the maximum length of the format (first {version} is dropped if even the rest without the title is too long, then the title is cut, finally the whole name; if neither the title nor the title ID would remain recognizable, the source name is used) and made suitable for Windows (no dot or space at the end; a reserved device name such as AUX gets an underscore). If the name matches an existing file, the program asks as usual whether to replace it; in batch conversion, a result of the same run with the same name is skipped. The template applies to every target format, .ffpkg included. If the details of the game are missing, the name of the source stays. On the command line, --ausgabename VORLAGE takes precedence over the setting.

Leftovers after an error. If a single run has failed or was cancelled, a card shows what was left behind: the unfinished result and, next to it, .teil, .neu, .part and .partial files, with sizes. Nothing is removed unless you ask for it. The source itself, a folder around it and a folder inside it are protected twice (when offering and when removing). In batch conversion and on the command line it stays with the log. When a game folder is moved (Task 4), sce_sys and, at the very end, eboot.bin are handled, so that an aborted half folder does not look like a game.

Delete the source after success. With the checkbox Delete the source after success in the path card (on the command line --quelle-loeschen) the program deletes the source as soon as the result is finished and verified – permanently, not to the recycle bin. Before the start it asks once more: Yes deletes after success, No converts and leaves the source in place, Cancel does not start. The checkbox applies only until the next program start. The source stays in place if the result is missing or empty, if the source has changed since the start, if result and source are the same path or one lies inside the other, and if the source is a drive, a user or system folder or a link; the run still counts as successful, and the reason is in the log. In batch conversion this applies to each source individually. If the source came from an archive, the archive is deleted.

Language at startup. Without a saved choice the program follows the display language of the system; if it does not know that language, English applies. A language chosen with the language button always applies.

5 Task 1 – Convert dump folder

What is this good for?

A dump folder becomes a single file. You need this when a game is to go on a USB stick: The console does not read a loose directory there, but a container that ShadowMount+ mounts.

The folder itself is left untouched – a copy in the chosen format is created. The only exception: With Dump folder (with integration) you explicitly choose “Into the original” (see below). If you want to turn an existing file back into a folder, use Task 2, 3 or 4.

Use Task 1 if your data is already available as a regular dump folder. As the result you can choose .ffpfsc (compressed), .ffpfs (uncompressed), a real .exFAT image or a UFS2-based .ffpkg.

If AMPR EMU (also with asset pack), PlayGo or BACKPORT is checked (Chapter 11), the list additionally contains Dump folder (with integration). In that case no image is created, but a dump folder with exactly these integrations – for example, to keep using it yourself afterwards. At the start, the program asks where to integrate:

  • Into a backup (recommended) – the dump is copied to the target folder, and only the copy is modified. Your original stays untouched; the copy needs the same amount of space once.
  • Into the original – the integration is made directly in the folder you chose. The program explicitly warns about this: Afterwards the files are no longer original. BACKPORT replaces eboot.bin and the libraries without a backup; AMPR EMU, asset pack and PlayGo add files. This cannot be undone.

If the backup would end up where the source is (the target folder is the folder that contains your dump, or a folder inside it), the program aborts and asks for a different target folder – or for “Into the original”. If a folder of the same name already exists in the target folder, you are asked before it is replaced. On the command line, the integration is always made in a backup.

  1. Click Dump folder and choose the folder you want.
  2. Open the TARGET FORMAT list and choose the format you need.
  3. If needed, adjust the compression level and worker threads.
  4. Choose the target and temp folders.
  5. Click START and wait for the success message.

The folder must carry the game in its root: eboot.bin and sce_sys/param.json are located directly in it, not in a subfolder – this is what ShadowMount+ requires of the root directory of an image. If eboot.bin is missing, the program aborts with a message before the build (for .ffpfsc, .ffpfs, .exFAT and .ffpkg alike), instead of the problem only showing up on the console.

Archive as source. In Task 1, the button Archive… is to the left of Dump folder: It chooses an archive (.zip, .7z, .rar), while Dump folder chooses the folder as usual; an archive can also be dragged onto the source field. The program unpacks it into the work folder (ps5conv_archiv_…, which must have at least as much free space as the size of the archive) and takes the game folder inside it – the one with sce_sys/param.json – as the source. Progress and result appear in the log. The program unpacks .zip itself; .7z and .rar are unpacked by the bundled 7-Zip (folder 7-Zip-26.06; if it is missing, the program looks for an installed one). The unpack folder is replaced at the next archive, and a leftover is cleaned up after twelve hours like any other work folder.

ZIP without an unpack folder. If the result is an image (.ffpfsc, .ffpfs, .exFAT or .ffpkg) and the conversion without an intermediate folder is switched on, the program no longer unpacks a .zip: only a small shadow folder with sce_sys and eboot.bin is created in the work folder – enough for cover, title, checks and naming – and the run reads the game itself directly from the archive. This saves the space and the time of unpacking; the log names the shadow folder. If the chosen route does need the game as a folder after all (target format dump folder, a route through an intermediate folder), the program unpacks the rest before the run – with a space check, and only if the archive has not changed since the shadow folder was created. .7z and .rar are always unpacked (they are usually packed solid and cannot be read at an arbitrary position), and so is an AES-encrypted ZIP.

If the archive is password-protected, the program first tries without a password, then the common passwords pippo and DLPSGAME.COM and after that your own list: under SETTINGS, section ARCHIVE PASSWORDS, you enter further passwords separated by commas; they are saved as you type. If none fits, the window asks for the password (the input field shows asterisks, and the password does not appear in the log) and asks again if one is wrong.

Task 5 (batch conversion) also accepts archives: They can be added to the sources in the file dialog (filter Archives) or by drag and drop and are processed in turn – each one is prepared only when it is needed (a ZIP as a shadow folder as above, otherwise unpacked) and removed again right afterwards, so there is only ever one work folder. A folder full of archives does not stand for the archives in it there; they are chosen individually. If an archive is encrypted and no password from the list fits, it counts as a failure of that source, and the others continue. The same applies on the command line: --source Spiel.zip for Task 1, several archives for Task 5, and --archiv-passwort specifies a password, which is then the only one tried.

If the memory runs out, the program restarts the run by itself – with half as many cores, up to three times – and writes this to the log. This is detected only if the engine itself reports MemoryError. If even one core does not help, the notice about too little memory remains.

If you are unsure

Keep the original dump folder. .ffpfsc and .ffpfs are compact bundles; .exFAT and .ffpkg are image and container formats, respectively, for suitable further workflows.

What is this good for?

The same for an .exFAT file. It is a real file system image.

11.1 Asset packs – storing the game files packed

The volumes are created when creating an image – or at the push of a button

Both dropdown lists belong to the integration performed when an image is created (tasks 1 to 6). The AMPR EMU Manager does not build any volumes on its own: it replaces the library, backs it up, removes it, or rebuilds the index – an existing asset pack is left untouched in the process.

Since v1.9.36 there is a dedicated button for this, Build asset pack (section 11.2). It runs only when the button is explicitly pressed, never as a side effect of another action in the Manager.

A button Remove asset pack has been dropped and will not come back: it deleted the manifest and volumes on the assumption that the original files were lying next to them, and since the choice described below that is no longer true in every case.

Next to the dropdown list for the AMPR build, there has been a second one with two entries since v1.9.8: Normal and Asset pack. It selects how the game files are stored – the library itself goes into the folder the same way in both cases.

Both dropdown lists must be set correctly
ListWhat to select
AMPR build 0.4.2.1 test-pack or 0.4.2.1 test-debug-pack

The third build, 0.4.2.1 test-nopack, cannot do it – and that is exactly the one that appears at the top of the list by default as the newest build without debug output. The selection must therefore be changed actively. Use test-pack for normal use; test-debug-pack additionally writes a log and is intended only for troubleshooting.

What the difference is

Normal is the previous route: the game files stay as individual files, exactly as they are in the dump.

With the new method they additionally go into packed volumes (ampr_assets-*.pak), which the AMPR EMU reads block by block from build 0.4.2.1 on. This saves space on the disk and file descriptors on the console. Nothing else needs to be done for this: writing the profile, packing, verifying, and placing the volumes in the game folder all happen in a single run.

Verification is against the source, not just against itself. Every block that is converted back is compared byte for byte with the original file. Only when this matches for every packed file is anything transferred to the game folder. A check without this comparison would only say that the volumes are consistent in themselves – not that they carry the game content.

Your original files stay in place – unless you say otherwise. At the start, the program asks once whether the packed originals should be left out of the result; the default is No. Removal happens only in the working copy, never in your own dump folder. On the command line the switch is --ampr-originale-weglassen. With AMPR EMU NG and zstd this question is skipped: the packed originals are always left out of the working copy. The same applies to NG with LZ4 when packing without an intermediate folder (Section 3.3); with the drakmor runtime the originals stay in the image, even if you chose “leave out”.

Console test first, then leave out

Whether a game really reads every file through the AMPR EMU is only shown by a run on the console – some titles bypass it (for example via mmap), and this goes unnoticed on the PC. The developer of the pack tools therefore requires the complete console test with the originals before any file disappears. So build the image with the originals first, play through it, and only then build it without.

This saves space only with .ffpfs, .exFAT and .ffpkg. An .ffpfsc compresses better than the volumes: with an asset pack it was never smaller in any measurement than without.

Since v1.9.31, files that the system itself reads always stay as ordinary files: cache_ps5/playgo.pgm, *.packman, the pgc_*_dummy_file files and the movies/ folder. Until then they went into the volumes as well and were deleted when the originals were left out – but PlayGo reads them bypassing the emulation, and the game crashed about one second after starting. In addition, after packing the program inspects the finished manifest and aborts if such a file is still in it.

Some games cannot run at all without the originals

The volumes serve only read operations that go through APR. Whatever a game engine reads with ordinary file access must be present as a real file in the image – otherwise it is simply gone after the originals are left out.

Measured on the console (September 20, 2026). A Unity game, built without the originals: the emulator reported “No such file or directory” for five files of the Unity runtime – so it did not serve them from the volumes –, the whole capture contained not a single apr.pack line, and the game exited shortly after starting. The same game with the same volumes and the originals alongside ran through.

Since v1.9.33 the program recognized such titles by their runtime files (data.unity3d, globalgamemanagers, global-metadata.dat, ScriptingAssemblies.json, RuntimeInitializeOnLoads.json) and left the originals in place.

That was not enough – measured on September 21, 2026. Arkanoid – Eternal Battle is not a Unity title; the detection found nothing, the originals were removed, and the image crashed on the console. The same source with the originals alongside runs. On closer inspection: .gnf texture atlases of up to 357 MB and ten FMOD .bank files – FMOD reads through its own file callbacks, and large atlases are mapped into memory. That makes two out of two attempts without originals that crashed, and no title has ever shown that the volumes are read.

Since v1.9.38 the originals therefore always stay in place as long as the pack profile comes from the program – even if you chose to leave them out. A list of engines cannot do the job: it would have to know every future one already, and the failure only hits you on the console. The detection remains, but it no longer blocks – it explains. If Unity is detected, its name along with the files found appears in the log; otherwise the general reasoning. The image does not get smaller as a result – but it starts.

Why the program does not simply exclude these files from packing. In the image that crashed, 197 of 259 files had been packed and removed – four of the five names were among them. The capture, however, contains not a single apr.pack line: so it is not proven that for this title any packed file was served at all – the four are merely the ones where it was noticed immediately. Excluding four more names would mean guessing that the remaining 193 hold up. And data.unity3d carries the entire game content in many titles; if it stayed loose, nothing would be left of the pack anyway.

The way forward is through captures. The pack profile of this program is generic: it cannot know what a particular title really reads through APR. Two classes are proven never to belong in a volume – the PlayGo files and the IL2CPP metadata –, and both apply to all games of their kind. Whether a title has a third class is shown only by starting it on the console.

Tested profiles are included for four groups of games (since v1.9.78). If the program detects ASTRO BOT, EA Sports UFC 6, a game on the Unity engine, or one on the Insomniac engine when packing, it applies the matching profile instead of the general one. The profiles come from the MkPFS.CSharp project by danthespal (GPL-3.0) and were verified there on a real PS5; they are located in the folder AMPR_PackTools-4.0\profiles. A title is recognized by its title ID in sce_sys\param.sfo (ASTRO BOT, UFC 6) or by its files (Unity, Insomniac). If your own profile applies (see below), none of this is touched. A bundled profile also counts as generated by the program: the originals therefore stay in place, and on the next packing run it is rewritten. Which profile was used is named in the first line of the file ampr_pack.toml, whose location is shown in the log (“built-in profile for …”).

How strongly to pack is set by you (since v1.9.80). Under SETTINGS, the section Asset pack (LZ4) holds the LZ4 level. The default is 9. Level 12, which was fixed until v1.9.79, saves only 0.0 to 0.6 percentage points more according to measurements on real game data, but takes 1.2 to 3.6 times as long; level 1 packs fastest and saves hardly any space. The level changes only size and packing time, not the format – the console reads every level the same way. It applies to the program’s general profile and to the bundled game profiles, not to your own profile (see below). On the command line it is set by --ampr-lz4-stufe (1 to 12).

Pack method in the main window. In the integration row, below the method (second row), there is the same LZ4 / zstd selection; it is the same setting as in SETTINGS. It can only be selected with AMPR EMU ticked and the method Asset pack; with Normal it stays grey and nothing is packed with LZ4 or zstd. If you choose zstd, the program takes the newest regular NG version unless an NG version is already selected; with LZ4 the version stays freely selectable.

Pack level and “Full verification”. To the right of the pack method is the pack level: it shows the levels of the chosen method (LZ4 or zstd) and is the same setting as under SETTINGS. Next to it, Full verification switches how thoroughly the packs are checked on their way into the image. Off (default): the structure, headers and position of every block are always checked in full, and of the content a sample (the first and last piece of large files plus random pieces, about 1 %; the seed is shown in the log). On: every byte. This applies to zstd and to LZ4 without an intermediate folder; if the program does pack LZ4 through an intermediate folder after all, the pack tool always checks everything.

LZ4 without an intermediate folder. LZ4 packs, too, are created without unpacking the game: the program compresses each block twice, once to measure and once when writing into the image, and holds each block against the measurement. The source is read twice in the process. With one track per group, the volumes are byte for byte the same as those of the pack tool. With ampr-emu-ng (NG) the default profile packs everything except the system files (eboot.bin, modules, sce_sys, sce_module, fakelib, .ini, the PlayGo files and global-metadata.dat); images, sound, video and configuration files therefore go into the volumes as well, because NG serves them like any other file. The packed originals are missing from the result; empty files remain as files in the image. With the drakmor runtime the more cautious default profile with the loose extensions applies (see below). If a run has to pack through an intermediate folder after all (Section 3.3), the originals stay, as with the answer No to the question. Checked on the console is NG with LZ4 without originals on two Unity games; the same image without the emulator shows only a black screen, so the volumes are served by NG alone. Large games and other engines have not been measured. The speed depends on the source: it is read twice, and with a slow disk (about 50 MiB/s) that takes a good six minutes for 11 GB.

Pack method LZ4 or zstd. Under SETTINGS, in the same section, select the Pack method. LZ4 (default) builds the volumes ampr_assets-*.pak and runs with all builds that read packs. zstd builds ampr_zstd.index and ampr_zstd-NNN.pak, packs every non-empty file except the system files (eboot.bin, modules, sce_sys, sce_module, fakelib, .ini files) in 256 KiB blocks and usually compresses more strongly. These packs are read only by ampr-emu-ng (NG); the runtime by drakmor does not know them. With zstd, the version list therefore shows only NG, and a run with a different build aborts without packing anything. The zstd level ranges from 1 to 22 (default 5, fast; 9 balanced; 19 small and slow). As with LZ4, every block is checked against the original file before anything goes into the game folder. On the command line it is set with --ampr-pack-verfahren zstd and --ampr-zstd-stufe (1 to 22). Custom pack rules: If a file <Ordnername>_ampr_pack.toml sits next to the dump folder, it also decides with zstd what stays loose ([pack] default_action with compress, store or loose, plus [[rule]] with action, include and exclude; the last matching rule wins, patterns like fnmatchcase). Instead of long lists in the rule, include_from and exclude_from can point to text files with one pattern per line (empty lines and lines starting with # do not count); the names are relative to the folder of the rule file, must stay inside it (no .., no absolute path, no link) and are appended to include or exclude respectively. Limits: 1 MiB per file, 16 MiB and 200,000 patterns in total, of which at most 10,000 with wildcards. The same rule file can also be chosen once in the Settings (Pack rules for zstd, button Choose …); it applies to every game for which no file sits next to the dump folder, and only with zstd. System files always stay loose; block size, hot and layout apply only to LZ4. A faulty file aborts the run before anything is written. The tool Asset pack check / unpack (MORE TOOLS) also opens zstd folders. Whether ampr-emu-ng really starts a game with zstd packs on the console has not been measured – the packed originals are missing from the result; keep the source dump (it stays unchanged).

Unsigned programs are fake-signed (since v1.9.92). If a game's eboot.bin and modules are plain ELF files, it never starts on the PS5 – the loader rejects them. When a task starts and the program finds such programs in a folder, it asks whether to write them as fake-signed SELF files when creating (as ps5-dump-forge does). Under SETTINGS in the section Unsigned programs this can be switched on permanently without asking; the program then also checks images, which it unpacks for that. It writes in the working copy or the unpacked folder; in the original folder a .orig of every file stays next to it. Already signed programs stay untouched, and the log names every changed file.

Already compressed files stay loose (since v1.9.80). The general profile does not pack images and textures (png, jpg, dds, gnf …), archives (zip, 7z, rar …), audio or video (ogg, wem, bnk, at9, mp4, bk2 …) or configuration files (json, ini, xml, txt …). LZ4 gains little there; the console also likes to read the configuration files from the disk itself. Across 37 measured dumps (1620 GB) this affects 24% of the data, mainly archives and videos. The four bundled game profiles and your own profile are not affected by this.

Empty files are not lost (since v1.9.80). The PS5 checks some empty files (such as language placeholders) outside the game; if they are missing, the game may get stuck on a black screen. When packed originals are left out, the program therefore recreates empty files after the removal.

Your own profile always takes precedence. Place a file named after the dump folder with the ending _ampr_pack.toml next to the dump folder – for example F:\Game Dumps\Mein Spiel_ampr_pack.toml next to F:\Game Dumps\Mein Spiel\. The program uses it, never rewrites it, and no longer holds you up about it: whoever packs from captures knows what the title reads through APR. The log then says “Custom pack profile adopted”.

Does this profile have to be written by hand? No. The AMPR trace assistant (button 10. AMPR trace in the CONSOLE view; it shows its page on the right and begins only with START) leads step by step through several real game runs on your PS5 and generates exactly this file automatically – named correctly and in the right place. Beforehand it checks whether ShadowMount+ really loads the recording library, switches over temporarily if desired and puts everything back at the end – the game must not be running during this. If the title is listed in the config.ini under fakelib_exclude, it asks before recording; it does not change this entry itself. If the program is closed while it is running, it waits for the restore and then closes by itself. A detailed, illustrated guide to the whole process (trace, checking the profile, building, leaving out the originals) is opened by the button LZ4 & Asset Pack Guide at the top in the title bar, to the left of USER MANUAL – operated exactly like this manual here. The file is also in the folder Anleitungen next to the program: AMPR_Asset_Packs_Mitschnitt_Assistent.html or .pdf.

11.3 PlayGo – the question comes before the work

Next to the AMPR EMU checkbox is PlayGo. It additionally places a stub for libScePlayGo.sprx in the game folder, which reports all language and scenario packages as installed. It is off by default, because most games do not need it: of 31 measured dumps, only one declared PlayGo content (sce_sys/playgo-scenario.json).

If a title declares such content and PlayGo is not checked, the program asks at the start of the run – before anything is copied, unpacked or packed – whether PlayGo should be switched on. Yes is preselected: the checkbox gets checked, and the stub goes into the result right away. With No, it continues without.

For a dump folder and for .exFAT, .ffpfsc and .ffpfs, the program looks into the image’s directory for this – in fractions of a second, without unpacking it. A .ffpkg cannot be looked into this way; there the question comes as soon as the files are unpacked, and still before the result is built. On the command line, no question is asked: a note appears in the log instead, and the saved setting applies.

DLC EMU. Below the AMPR EMU checkbox is DLC EMU (drakmor/dlc_emu 0.3). It places three replacement libraries – libSceAppContent, libSceNpEntitlementAccess and libSceGameUpdate – in the fakelib folder and thereby reports additional content as present. Which ones is defined in the dlc_emu.ini in the game folder. An existing file is left unchanged; if it is missing, the program creates it from the content IDs in dlcmap.json, as a fallback from the complete ones in eboot.bin (without the ID of the game itself) and notes in the log that the entries need to be checked. Without a matching file, the libraries report no additional content. A game original of one of these libraries is backed up once as .orig. If the game has additional content – a dlcmap.json of the game with entries, a DLC folder of the PS5 App Dumper (…_00-…-ac) next to the game folder, a dlc_emu.ini or a filled addcont… folder – and DLC EMU is not checked, the program asks before the work, as with PlayGo, whether it should be switched on. This applies to dump folders and images (for images, the names dlcmap.json, dlc_emu.ini and addcont… count); a .ffpkg cannot be looked into, so there only a note appears in the log. The program copies such DLC folders into the game as addcont0, addcont1 … and enters them with a mount point in the dlc_emu.ini; all other additional content that merely unlocks something appears in it as a pure entitlement. Like AMPR EMU and BACKPORT, the integration works on the dump folder and thus applies to all target formats; it comes before the AMPR EMU, so that its index knows the new files.

A good first step

12.1 What is additionally checked for .ffpfsc and .ffpfs

These containers have a two-level structure: the container on the outside, and inside it exactly one image holding the game files. If something went wrong during creation, another level may have ended up in between by mistake – from the outside the file then looks completely normal, but it is unusable on the console.

Task 8 therefore looks one level deeper and reports in the log:

LineMeaning
nesting: in OrdnungThe game files are on the innermost level – as it should be.
nesting: falsch verschachteltAnother image is there instead of the files. The file must be created again.
inner_files / inner_dirsNumber of files and folders on the innermost level.
nesting: flach aufgebautThe files are directly in the container; the inner image is missing. Appears, for example, when checking an intermediate result.

The check does not unpack the file for this: it only reads the table of contents of the inner level – for a 392 MB file, about 750 kilobytes in under a tenth of a second.

12.2 Unpack check for .ffpfsc

The payload data of an .ffpfsc is stored compressed, and every block carries its own checksum. Simply reading the file does not reveal a damaged block – the storage device delivers it without complaint. Task 8 therefore additionally unpacks every block (without saving anything) and reports in the log:

LineMeaning
payload: in OrdnungAll blocks can be unpacked and match their checksum.
payload: beschädigtAt least one block cannot be unpacked – typical of an interrupted copy or transfer. Copy the file again or create it again.
payload: nicht prüfbarThe file is uncompressed (.ffpfs) – it has no checksums that could be compared.

This takes as long as unpacking does – several minutes for a large title. The bar shows the first half for this, and the subsequent reading for the SHA-256 checksum the second; CANCEL takes effect immediately in both parts.

Limit: An .ffpfs, an .exFAT and an .ffpkg carry no checksums for their payload data, and neither does a block that the engine stored uncompressed. Task 8 does not notice a corrupted bit in the middle of the game data there. Structure, size and file system are still checked; anyone who wants to be sure compares the checksum (SHA-256) of the copy with that of the original.

For an .exFAT, Task 8 additionally checks the beginning of the image: the name “EXFAT” in the boot sector and the checksum of the boot region. If the name is missing or the checksum does not match, the file is damaged (no longer just a note); the same applies to an .ffpfs/.ffpfsc with an unknown header.

Before starting, the program checks the sources of Tasks 1 to 6 for a plausible signature at the start of the file: an empty, wrongly named or truncated .exfat or .ffpkg is rejected with a message instead of “successfully” producing a small, unusable result.

Unchecked is not a verdict

An .ffpkg is checked via UFS2Tool, and that requires administrator rights. If they are missing, the result since v1.9.1 is UNCHECKED – no longer “failed”. The difference matters: failed means something was found; unchecked means nothing was looked at. It says nothing about the file. Start the program as administrator and check again.

In command-line mode, Task 8 returns the exit code 4 for this – neither 0 (OK) nor 1 (flagged).

Trophies: PS4 titles do not register from an image

A PS4 game that starts from an image reports Trophy registration failed (0x80551618) and does not register its trophies – on every start, again and again.

This is by design. The error code comes from Sony's NPDRM check chain, and that requires a regularly installed package. A mounted image is not one. So it is not the fault of the image, of the conversion or of ShadowMount+.

PS5 titles are not affected. On August 22, 2026, every title on the console was checked to see whether its trophies are registered: six PS5 titles ran from images and all six had them registered. Only the PS4 title did not. PS5 games go through a newer trophy chain, PS4 games through Sony's old one – and only the old one requires installation.

Adding files does not help. What was tried was npbind.dat and param.sfo in /system_data/priv/appmeta/<Title-ID>/, the same file in the subfolder trophy2/, and finally the complete registration entry under /user/trophy/conf/, rebuilt by hand. After the game started it was still there unchanged: the system had not even looked at it. So the block sits in the console's program code, not in missing files.

If you need the trophies, install the game via the Package Installer. The same title then registers on the very first start. You can check on the console: under /user/trophy/conf/ there is a folder for every registered PS4 title.

For everything else the image route remains the more convenient one – it saves the storage space of the installation. Just without trophies.

If a game gets stuck on the loading screen

Some titles from the image stop at a “Please wait” instead of switching to offline operation. The same package installed via the Package Installer shows its offline dialog and carries on.

Measured and ruled out: the storage location on the storage device, missing PlayGo content, an online query (the console was taken off the network entirely – same hang) and an incomplete image (compared file by file, nothing was missing). The cause is open. By no means every title is affected – trying it decides.

Two build forms occur in real dumps. 14.6 BACKPORT – Lowering games to an older firmware

A PS5 game remembers which development kit (SDK) it was built with. At launch, the console compares this with its own firmware and does not start anything that is too new. If a game requires firmware 9.00 while your console is on 4.50, simply nothing happens when you tap it. BACKPORT lowers this value.

Where to find it: MORE TOOLS → BACKPORT. Then select the game folder.

The procedure

  1. Choose the folder. The game's dump folder, that is, the one containing eboot.bin and sce_sys.
  2. Set the target firmware. The choices are 4.00, 5.00, 6.00 and 7.00 – choose your console's version or a lower one.
  3. See what would happen. On opening, the list already shows every executable file with its current SDK and what would happen to it. The Analyse only button repeats this without changing anything.
  4. Start the backport. After a confirmation prompt, the program works through the list.

The settings

Off by default; without a readable import table, the full set is used. The choice also applies to integration during creation.

What is protected in the process

Work takes place exclusively in memory. A file is only replaced once unpacking, lowering and re-signing have all succeeded – and then in a single step. If any step fails, the original stays exactly as it was. An SDK value is never raised, only lowered.

Important

The result is re-signed, but not genuinely signed – it only runs on a console that is already jailbroken. And whether a particular game actually starts after the backport cannot be predicted: some games require functions that simply do not exist on the older firmware. Therefore always work with the backup switched on, and keep the backup folder until you have successfully started the game on the console.

The two hosts (webkit-autoloader-host_vX.Y.Z.exe and .py) are not bundled with the program: on the first click on Start host, it downloads the host of the selected version from the author's release (with a progress display, the SHA-256 is verified) into the settings folder and starts it right away; every further click starts the saved file. If the file is gone afterwards, the antivirus has usually removed it – allow it there if you trust it. When a new version appears, put its installer in addition into that folder; the older ones stay and remain selectable. The program reads the folder when the page is built: the new version then appears in the selection, the newest first (sorted by the numbers in the name: 0.10.0 comes after 0.9.0). Nothing has to be changed for this. A file without a number in its name does not appear in the selection; it is used only if there is no version with a number at all. At the next build, the folder contents go unchanged into the finished program.

14.11 Send unjail – Lifting Homebrew out of the Sandbox

Homebrew applications run on the console in a folder of their own and may write only there. Some need more – they then ask for extended access. unjail is a small console daemon that answers exactly these requests. It is sent once and then runs until the next restart of the console.

Found under: MORE TOOLS → Send unjail. Enter the address of the console and click Send to PS5 – progress and the reply of the console appear in the window meanwhile.

It makes sense before starting a homebrew that needs extended write access. For ordinary conversions with this program, unjail is not needed.

Only up to firmware 10.60

unjail is verified for firmware 1.00 to 10.60. From 11.00 on, the daemon aborts at startup before it is ready – on a console with 11.00 or newer it currently does not work. The window points this out before sending.

14.12 PS5 Wee Tools – the Console's NOR Flash

PS5 Wee Tools by andy-man is a bundled third-party tool (GPL-3.0) – not part of the conversion. It does not work with game dumps but with the NOR flash of the console: from a NOR dump it reads model, SKU, region, serial numbers, firmware and MAC addresses, splits the dump into its partitions and reassembles it, shows the UART log including EMC error codes, and can read and write the NOR via an SPI flasher (SPIway on a Teensy 2.0).

Found under: MORE TOOLS → PS5 Wee Tools (NOR). After a confirmation prompt, the tool opens in a console window of its own, on Linux and macOS in a terminal. The start can take up to a minute: on Windows and Linux, the program file unpacks itself a second time for this (measured on Windows: 19 to 48 seconds). Do not click again in the meantime – a second start opens a second window. It is operated there with numbers and letters; 6 in the main menu quits it.

It stores read NOR dumps (dump_*.bin) and UART logs (uart_*.txt) in the PS5 Wee Tools folder next to the program (on macOS in the settings folder); it also remembers language, sound and connections there. On the first start, it takes over the language from the program.

A NOR written incorrectly makes the console unusable

Reading is harmless. Writing the NOR and switching flags (kiosk mode, model, active slot) change the console's firmware memory. Keep a backup of the original dump beforehand. The flag switch writes without confirmation directly into the opened file – so work with a copy.

14.13 ELF → EBOOT.BIN – Packaging an ELF as eboot.bin

Packages an executable ELF file – for example a self-built homebrew – as eboot.bin: a SELF wrapper with the ELF inside, the way the PS5 launches it.

Found under: MORE TOOLS → ELF → EBOOT.BIN. Choose the .elf, then the save location (the suggestion is eboot.bin in the same folder). Packaging uses the same method with which BACKPORT (14.6) resets files. Afterwards the program reads the result back as a check; only when it appears there as a SELF with an embedded ELF does the window report success – with the size before and after and the number of segments.

  • For jailbroken consoles only. The eboot.bin is a fake SELF without a real signature and is not compressed. The packaging itself is tested (BACKPORT has used it for a long time); the program has not yet tested launching an eboot.bin created this way on the console.
  • What is rejected: a file that is already a SELF (it does not need to be converted), a stripped ELF without an identifier at the start of the file, and anything that is not an ELF.
  • No half-finished state. Writing goes to a temporary file first, and only then does it replace the target. Even if you choose the source itself as the target, it stays intact until the very end.

The structure of the result is shown by the SELF inspector (14.1).

14.14 EDIT IMAGE – Changing Files in an Image

Rename, delete, replace or add files of a finished image – in two ways: Edit in place writes into the image itself (.exfat, .ffpkg and uncompressed .ffpfs), Unpack takes the route the program takes elsewhere too: unpack, change, repack – for every format, .ffpfsc included.

Found under: MORE TOOLS → EDIT IMAGE.

Edit in place (without unpacking and rebuilding):

  1. Choose the image, Edit in place. The program asks whether the image itself really should be changed and then shows its content in the tree – read from the image, without unpacking.
  2. Change as below (Rename, Delete, Replace …, Add …, New folder). Every change is only queued at first: the tree already shows the new state, while the file stays untouched. Whatever is not possible (name already taken, no room) is rejected – and then nothing is queued either.
  3. Apply changes. Only now is anything written, in the background: first the old bytes of every affected spot into a journal next to the image (<Abbild>.undo), then the new content, and finally the file system's management data. If writing is interrupted (crash, power loss), the program reverses it the next time the image is opened, using the journal, and tells you so. A change that has been applied completely cannot be taken back this way. If you close the window with queued changes, the program asks and discards them.
  • .exfat never grows. Images made by this program have no free cluster; room is made by deleting or by replacing with a smaller file.
  • .ffpkg (UFS2) never grows either, but has some reserve because the program adds room when building it. It recalculates the bitmaps and counters of the file system after every change the same way it creates them when building.
  • .ffpfs (flat PFS – this is how the program builds .ffpfs): new content goes into free gaps or is appended at the end, so the image grows as needed; the space of a deleted or replaced file is used again next time. The program rebuilds the directories and the path table when applying, exactly as MkPFS would build them for the same content. A PFS knows no empty folders: a new folder needs at least one file by the time you apply. An .ffpfs that merely wraps an inner exFAT image is changed like an .exfat.
  • Not in place: .ffpfsc (compressed) cannot be edited this way – use Unpack for it.
  • Tested is the in-place route with independent readers: exFAT with the exFAT driver of the Linux kernel, UFS2 with UFS2Tool (fsck_ufs, extract and a probe that fills the free space and then compares all files), PFS with the MkPFS check against a folder with the same changes. On the console, an .ffpkg and an .ffpfs changed this way ran without errors (one small game each: mount, start, play, quit) – still, try with a copy first.

Unpack (every format):

  1. Choose and unpack the image. The program unpacks it with Task 6 (target dump folder) into a work folder – with all the checks and prompts of that task; progress and log appear as usual in the main window.
  2. Change. Select an entry in the tree: Rename, Delete, Replace … (the content of the file is replaced by another one, name and location stay), Add … (new files into the selected folder) and New folder. Every change takes effect immediately in the work folder.
  3. Save. Choose the format (the original's is preselected), Save as image …, choose the target folder. The result is named <Name>_bearbeitet.<Endung>; the original stays unchanged. It is also possible to save to a different format or to save several times.
  • Protected are eboot.bin and sce_sys/param.json – on both routes: they can be replaced (for example by a patched eboot.bin) but not deleted or renamed, and neither can the folder that contains them. If one of them is missing when saving, the program asks first.
  • Names must be valid on the console and under Windows; two names that differ only in upper/lower case count as the same. Links are not touched, and nothing can leave the game folder.
  • Space: The work folder (unpacked game) and the new image need space together; the work folder is in the configured temp folder and is removed when the window is closed. If there are changes not yet saved, the program asks first.
  • Tested is the whole route on a small .ffpfsc (unpack, replace, rename, add, save, unpack the result again and compare). Whether a game changed this way starts on the console depends on what you changed – try with a copy first.

14.15 Devices on the network – NAS and Computers as Source or Target

Finds NAS devices and computers on your own network and sets their Windows share as the source or target. Found under: MORE TOOLS → Devices on the network.

  1. Search. The search takes a few seconds; it finds whatever announces itself on the network (mDNS and WS-Discovery). The network is not scanned, and no addresses are tried out. Stop ends the search.
  2. Choose as source … / Choose as target … opens the folder dialog on the device's share (\\Adresse\); the chosen folder goes into the SOURCE or TARGET FOLDER field. The program reads and writes there without an intermediate copy.
  3. Copy address puts the address on the clipboard, for example for another program.
  • Devices with a Windows share (SMB) and computers can be chosen. FTP and NFS devices are only displayed.
  • If the search finds nothing, the device's network discovery is usually switched off. A share can also be entered into the field by hand as \\Adresse\Freigabe.
  • Tested is reading and writing through a share on your own computer (\\localhost); it has not yet been measured with a real NAS.

16.2 The environment check (“Doctor”)

If something does not work although it works for others, the environment check answers the most common causes in a few seconds. It is called from the command prompt or from PowerShell, in the program’s folder:

PS5_Dump_Image_Converter.exe --doktor "E:\PS5_Temp" "E:\Ziel"

Both folder arguments are optional. Without them, the system’s temp folder is checked.

Open as administrator

The program always requires administrator rights – this applies to every call, including the environment check. Therefore open the command prompt or PowerShell yourself as administrator, otherwise Windows refuses to start it.

Each line starts with its rating: [ ok ] fine, [ !! ] a note, [FEHL] a real error, [ -- ] not needed or cannot be determined. Among other things, the following are checked:

  • Long paths. If they are turned off in Windows, packages with deep folder structures abort – often with a message that sounds like something completely different.
  • The file system of the folders. On FAT32, every file ends at 4 GB; a dump is always larger, and the abort would only come after hours.
  • Free space and write permission for the temp and target folders.
  • The bundled programs – whether they can be started at all.
  • The settings file. If it is damaged, the program starts with default values; it then looks as if it had forgotten everything.

The output is suitable for copying into an error report. It contains no credentials and makes no connection to the internet. The same information is shown in the DIAGNOSTICS window in the Doctor section.

Unlike on Windows, there is no ready-made file to download: a Linux program is tied to the architecture and the system libraries of the computer on which it was built. It is therefore built on your own system. This takes a few minutes and is done with two commands in the project folder:

chmod +x Build_Linux.sh
./Build_Linux.sh

The script checks the prerequisites, fetches the required packages, and places the finished file under dist/. If Tcl/Tk – the foundation of the interface – is missing, it gives the appropriate install command for your system.

chmod +x Install_Linux.sh

20 The Application on the Mac

The program also runs on a Mac with macOS 11 (Big Sur) or newer – on Apple silicon as well as on Intel models. The interface, all eight tasks, and the additional tools look and work there exactly as described in this manual. This chapter covers only the differences.

20.1 What you need beforehand

A Mac does come with a Python, but it is unusable for building the program: it lacks the foundation for the windows. Therefore install a complete Python beforehand – either the installer from python.org or via Homebrew with brew install python-tk. The build script checks this and tells you exactly what is missing before it begins.

20.2 Building the program

As on Linux, there is no ready-made file to download: the program is tied to the architecture of your Mac. A version built on Apple silicon does not run on an Intel Mac and vice versa. Two commands in the project folder are enough:

chmod +x Build_macOS.sh
./Build_macOS.sh

This takes a few minutes. At the end, the finished program PS5 Dump & Image Converter.app is under dist/ – an application bundle, as you know it from any Mac program. A double-click starts it.

Do not build with sudo

Building does not need elevated rights. If it is started as root anyway, the result folder afterward belongs to root and can no longer be cleaned up on the next run.

20.3 Placing it in the Applications folder

So that the program sits in its usual place in Launchpad and in the Finder:

chmod +x Install_macOS.sh
./Install_macOS.sh

If the Programme (Applications) folder is locked, the script places the program in your personal Applications folder. This needs no password and appears in Launchpad just the same. You can undo this with ./Install_macOS.sh --entfernen; your settings are kept.

“The developer cannot be verified”

This message appears when the program reached you via browser, mail, or AirDrop – macOS flags everything that comes from outside. The install script removes the flag itself. By hand, it works like this:

xattr -dr com.apple.quarantine "/Applications/PS5 Dump & Image Converter.app"
